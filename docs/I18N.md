# Internationalization (i18n)

**There is no i18n in aiball today. English is the default — and the only —
language for all user-facing content.** This doc makes that explicit AND
sketches the intended approach for *when* we add translations, so it's a small,
well-scoped project — easy to add a language (YAML files, à la Symfony).

## Policy

- **User-facing strings are English.** UI labels, button text, dialogs, toasts,
  empty states, system/audit message bodies (e.g. the ticket-move audit comment,
  `🔀 Ticket moved from X to Y`), and API error messages — all English.
- **Docs are English** — this `docs/` folder and the root `README.md`. (Repo
  convention: docs must be in English.)
- **Code comments stay French.** The codebase is commented in French; that's a
  developer convention, *not* user-facing, and is out of scope here — don't
  rewrite comments.
- **No i18n framework.** There is no locale catalog, no `t(key)` lookup, no
  per-user/per-project language preference. Don't introduce one unless a ticket
  explicitly requests it.

## When you add a string

Write it in English. If you spot a stray French *user-facing* string, fix it to
English in passing — that cleanup pass did exactly that for the ticket-move
audit body and the comment-delete UI (confirm dialog, toast, tombstone).

## Proposed design (when we add i18n)

Not built yet — but here's the intended approach so it's a small, well-scoped
project when someone picks it up (#zkt342). **Design goal: adding a language is
easy** — drop a YAML file, fill the keys, done. Same shape as Symfony's
`translations/`.

### Catalogs — YAML, one file per locale

```
locales/
  en.yaml      # source of truth + fallback
  fr.yaml
  …
```

Symfony-style `key → string`, nested for grouping, `{param}` placeholders:

```yaml
# locales/en.yaml
ticket:
  moved: "Ticket moved from {from} to {to}"
comment:
  delete:
    confirm: "Delete this comment? It will be removed from the thread."
    button: "Delete"
    tombstone: "comment deleted by {by}"
```

```yaml
# locales/fr.yaml  (only the keys you translate; the rest fall back to en)
ticket:
  moved: "Ticket déplacé de {from} vers {to}"
comment:
  delete:
    button: "Supprimer"
```

### Lookup — one `t(key, params)` helper

- The **same** helper in the **frontend** (Vue components) and the **backend**
  (message/audit body builders + API error strings): `t("ticket.moved", { from, to })`
  interpolates the `{param}` placeholders.
- **English is the fallback**: a key missing in the target locale resolves from
  `en.yaml`, so a half-translated locale never shows a blank — it shows English.

### Locale selection

- A `locale` preference, default `en` — per **consumer** (a `locale` column on
  `consumers`) and/or per **project**; resolve consumer → project → `en`.
- Frontend reads it from the consumer; the backend renders a message/ping body
  in the recipient's locale (or stores `key`+`params` and renders per-reader —
  decide at implementation time).

### Migration path — incremental, no big-bang

1. Add the `t()` helper + `en.yaml` (seed keys as strings are touched; no need
   to extract everything up front).
2. Replace hardcoded strings with `t("…")` keys opportunistically — same spirit
   as today's "fix French on sight".
3. Add `fr.yaml` (or any locale) when wanted: translate only the keys that
   exist, the rest fall back to English.

### Effort

Small-to-medium: the helper + catalog loader is the only genuinely new
infrastructure; the rest is incremental string-keying. Track it as its own
ticket when it's wanted.
